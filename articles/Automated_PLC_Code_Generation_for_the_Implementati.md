# Автоматизована генерація коду ПЛК для реалізації алгоритмів керування на основі режимів у будівлях

Cai, X.,Jin, Z.,Li, H.,Kümpel, A.,& Müller, D.(2024). Automated PLC Code Generation for the Implementation of  Mode-Based Control Algorithms in Buildings. *Buildings*, *14*(1), 73. https://doi.org/10.3390/buildings14010073    

## Анотація

Неправильне програмування функцій керування у системах автоматизації та керування будівлями (BACS) може призвести до неефективної експлуатації будівель. Для зменшення помилок програмування перспективним рішенням може бути автоматизований процес реалізації функцій керування. Останнім часом інформаційне моделювання будівель (BIM) сприяє цифровізації будівельних проєктів, але рідко використовується під час планування та впровадження функцій керування у BACS. Опис керування у BIM також залишається невизначеним. Для вирішення цих проблем метод документування керування для BIM та автоматизований підхід до реалізації керування можуть спростити впровадження керування у BACS та, таким чином, покращити експлуатацію будівель. У попередніх роботах ми розробили метод MODI для структурованого процесу планування алгоритмів керування на основі режимів для систем енергозабезпечення будівель. Цей метод показав потенціал для підтримки цифрового планування та реалізації керування у BACS. На основі цього у цій статті ми представляємо метод документування для опису алгоритмів керування на основі режимів у форматі IFC (Industry Foundation Classes), що дозволяє обмін даними між BIM, та програмно підтримуваний підхід для автоматичної генерації коду ПЛК для реалізації цих алгоритмів. У випадковому дослідженні продемонстровано документування бажаної стратегії керування на основі режимів для мережі енергозабезпечення у форматі IFC та реалізацію цієї стратегії у програмі ПЛК. На етапі моделювання ми тестуємо реалізовану стратегію керування для перевірки функціональності програми ПЛК. Результати доводять, що стратегії керування на основі режимів можуть бути повністю автоматично реалізовані у програмі ПЛК на основі даних IFC.

**Ключові слова:** цифровізація будівель; автоматизована генерація коду ПЛК; алгоритми керування на основі режимів

## 1. Вступ

Сектор будівель становить 30% від загального кінцевого споживання енергії у світі та 27% від загальних викидів парникових газів [1]. Для зменшення великої частки споживання енергії у секторі будівель підвищення енергоефективності будівель стає важливим. Однак у будівельній галузі часто зустрічається розрив у продуктивності [2,3]. Цей розрив представляє невідповідність між запланованою та фактичною виміряною енергетичною продуктивністю у контексті споживання енергії будівлями, а також вказує на нереалізований потенціал ефективності будівельного фонду [3]. Як показано в огляді у [2], цей розрив у продуктивності розглядається у різних контекстах протягом життєвого циклу будівлі, таких як кліматичні умови та налаштування керування. Системи автоматизації та керування будівлями (BACS) також є ключовими чинниками підвищення енергоефективності та, відповідно, зменшення цього розриву [4,5].

Нещодавно вплив BACS на експлуатацію будівель було розглянуто у кількох дослідженнях, які довели, що ефективно спроєктовані BACS можуть зменшити споживання енергії та викиди CO2 у секторі будівель [5–8]. Примітні приклади включають обговорення у [5,6] стратегій управління знаннями для покращення проєктування BACS, у [7], що підкреслює інтеграцію Інтернету речей (IoT) у BACS для підвищення продуктивності будівель, та у [8], що фокусується на тестуванні контурів керування для підтвердження важливої ролі BACS у досягненні енергозбереження. Згідно з дослідженням у [9], ефективно налаштовані BACS можуть навіть заощадити до 30% енергії на опалення в офісній будівлі. На жаль, поточне проєктування та введення в експлуатацію логіки керування у BACS все ще значною мірою залежать від текстових описів, електронних таблиць та двовимірних креслень для обміну інформацією, а також від ручного програмування програмістами з керування [5,10–13]. Така низькоцифрова документація логіки керування є нестандартизованою та неоднозначною, потребує додаткової інтерпретації та залишає простір для різних варіантів реалізації. У процесі впровадження програмісти вручну кодують функції керування відповідно до специфікацій або безпосередньо використовують коди з існуючого подібного проєкту [14]. Цей процес є неефективним і може бути схильним до помилок [15]. Більше того, застосування низькоцифрового способу документування може також призвести до непередбачених втрат інформації на різних етапах проєкту.

Для зміни цієї ситуації перспективним є цифровий підхід до проєктування керування, програмування коду та введення в експлуатацію [16]. Для підтримки цього напряму у попередній роботі ми представили так званий метод MODI, який дозволяє систематичний процес розробки алгоритмів керування на основі режимів для систем енергозабезпечення будівель [17–19]. Алгоритми керування на основі режимів залежать від робочих режимів та їхніх переходів для організації роботи системи. Робочий режим визначає поведінку системи шляхом визначення роботи всіх компонентів у системі. Переходи активують переходи від одного робочого режиму до іншого та, зрештою, визначають поточний використовуваний робочий режим. Використання сигнально-інтерпретованих мереж Петрі (SIPN) як формалізованого методу опису у цьому методі забезпечує опис алгоритмів керування без неоднозначностей та непорозумінь, а отже, запобігає помилкам у процесі реалізації [18,19]. На основі цього ми розробили програмно підтримувану структуру для впровадження алгоритмів керування на основі режимів у програмовані логічні контролери (ПЛК) шляхом автоматичної генерації коду ПЛК мовою програмування Structured Text (ST) [20]. Розроблене програмне забезпечення збирає інформацію про конфігурацію алгоритмів керування на основі режимів через графічний інтерфейс користувача (GUI), а потім генерує відповідну програму ПЛК. Проте програмне забезпечення, розроблене у попередній роботі, вимагає ручного введення інформації про конфігурацію, що може бути як обтяжливим, так і схильним до помилок. Цю проблему можна ефективно вирішити, якщо дозволити програмному забезпеченню безпосередньо інтерпретувати алгоритми керування на основі режимів із цифрового джерела даних, такого як Industry Foundation Classes (IFC), а не покладатися на GUI. Тому у цьому дослідженні ми представляємо нову методологію документування алгоритмів керування на основі режимів у форматі IFC та подальшої їх автоматизованої реалізації у ПЛК шляхом генерації коду ПЛК.

IFC є відкритою схемою даних і сприяє експорту та обміну даними між інструментами інформаційного моделювання будівель (BIM) [21]. BIM представляє фізичні та функціональні характеристики будівлі у цифровому форматі та, таким чином, широко використовується у сфері архітектури, інженерії, будівництва та експлуатації (AECO) [22–25]. BIM підтримує обмін даними та інформаційну інтероперабельність протягом усього життєвого циклу будівель [26]. Типові інструменти планування BIM, такі як Revit [27] та ArchiCAD [28], використовують власні формати даних для зберігання внутрішніх даних [5]. IFC стандартизовано як ISO 16739 [29] і підтримує інтероперабельність цих інструментів BIM шляхом обміну даними BIM між ними [21]. У IFC набір загальних об’єктів будівлі визначається як відповідні елементи IFC з пов’язаними властивостями та атрибутами, які можуть бути інстанційовані та застосовані для конкретних випадків використання. Тому дані BIM на основі IFC здатні забезпечувати стандартизоване цифрове джерело даних та дозволяють обмін даними для функцій керування будівлею на етапах проєктування, введення в експлуатацію та навіть експлуатації [30]. Однак описи функцій керування у поточному програмному забезпеченні BIM та IFC є обмеженими [29]. Порівняно з іншими системами будівлі, проєктування BACS не розглядається у циклі проєктування та будівництва BIM, а зазвичай інтегрується на пізнішому етапі, тобто на етапі управління об’єктом [23]. Таким чином, інструменти BIM та IFC рідко використовуються для обміну інформацією про BACS [23,31,32]. Більше того, методи, що дозволяють опис функцій керування у IFC, залишаються неясними [29]. Формалізований метод опису функцій керування будівлею може бути корисним для цифровізації проєктування та реалізації функцій керування у BIM [29,33–35].

Щоб вирішити це питання, у цій статті ми досліджуємо новий метод опису для опису алгоритмів керування на основі режимів у форматі IFC, а потім інтегруємо IFC з розробленим програмним забезпеченням для автоматичної генерації коду ПЛК для реалізації алгоритмів керування на основі режимів. Таким чином, на основі схеми IFC будується ієрархічна структура для представлення даних. Файли IFC, що містять алгоритми керування, можуть бути імпортовані у програмне забезпечення для генерації відповідного коду ST та реалізації цього коду у програмі ПЛК для BACS. Стаття структурована наступним чином: у розділі 2 представлено методологію документування алгоритму керування на основі режимів у IFC та детально описано процес автоматизованої генерації коду ПЛК. У розділі 3 представлено приклад використання та обговорюються результати. У розділі 4 підсумовано основні результати та окреслено наступні кроки.

### Сучасний стан

Системи автоматизації та керування будівлями (BACS) відповідають за моніторинг та керування середовищем у будівлі та її безпекою, такими як пожежна безпека, освітлення та кондиціонування повітря [36–38]. У BACS виділяють два рівні керування: один — це процесне керування, яке здійснюється за допомогою безперервних та лінійних контролерів, таких як ПІД-контролери, інший — автоматизація будівель, що реалізує дискретні стратегії керування за допомогою текстових або графічних інструментів програмування. Залежно від складності функцій керування, два основні типи контролерів, що застосовуються у BACS, визначаються як програмовані логічні контролери (PLC) та прямі цифрові контролери (DDC) [37–39]. Завдяки надійності та простоті налаштування, системи автоматизації на базі PLC часто віддають перевагу під час проєктування BACS [40]. Стандарт IEC 61131-3 [41] стандартизує базову програмну архітектуру та виконувані мови програмування для PLC. Цей стандарт був розширений об'єктно-орієнтованими компонентами протягом останніх років [42]. Мови програмування, що підтримуються IEC 61131-3, включають дві текстові мови програмування, а саме structured text та instruction list, та три графічні мови програмування: ladder diagram, function block diagram та sequential function chart.

У різних галузях програми PLC історично були відносно простими. Однак останніми роками зростає попит на складні, розгалужені та модульні програми PLC. Мотивація зменшення ручної роботи при програмуванні PLC стимулює низку робіт, що представляють методи автоматичної генерації коду PLC, особливо в галузі виробництва та виробничих процесів [43–51]. У принципі, генерація коду є реалізацією вихідного коду у конкретному синтаксисі цільового коду, що відповідає семантиці вихідного коду [47,52]. Як демонструють Daniel Darvas та ін. [51], генерація коду може здійснюватися на основі формальних методів. Таким чином, у їхній роботі представлено мову формальної специфікації PLCspecif та розроблено відповідний генератор коду. Цільовим кодом є ST. Проте формальні методи та генерація коду не є широко впровадженими на практиці [52–54]. Однією з причин може бути те, що практики PLC зазвичай мають технічну освіту та обмежені знання у галузі інженерії програмного забезпечення, тоді як теоретичні концепції формальних методів походять з комп'ютерних наук.

У зв’язку з цим деякі роботи обирають генерацію коду PLC шляхом повторного використання існуючих програм PLC та мов моделювання загального призначення, таких як UML та SysML. Наприклад, Vogel-Heuser та ін. [45] визначають три загальні підходи до генерації коду PLC: підхід на основі шаблонів, модульний підхід та підхід на основі параметрів. На основі підходу на основі шаблонів функціональні блоки компонентів можуть бути перетворені на шаблони для повторного використання, які зберігаються у бібліотеці генератора коду та можуть вибиратися за заданим випадком [46,47]. Модульний підхід також є типовим для інтенсивного повторного використання програм PLC. Цей підхід вводить модуль, що складається з деяких компонентів, які представляють типову систему у промисловості, таку як установка або повна станція, та її логіку керування [44,50]. Fischer та ін. [49] демонструють концепцію на основі параметрів для повторного використання існуючих програм PLC, аналізуючи програму PLC для систем зберігання як приклад використання, у якому визначаються придатні до повторного використання коди та різні частини, які можуть бути оголошені за допомогою набору параметрів. Існують й інші роботи, що зосереджуються на інтеграції формального методу у добре побудований інженерний інструмент та практичний робочий процес. Багато виробників систем керування розробили інструменти для автоматичної генерації коду PLC [55], такі як Beckhoff TwinCAT automation interface [56], Schneider Unity Application Generator [57] та Mitsubishi Adroit Process Suite [58]. Ці інструменти надають можливість інтеграції у попередньо визначений робочий процес, налаштований програмістами PLC.

Наскільки нам відомо, генерація коду PLC ще не є широко застосовуваною під час реалізації логіки керування у сфері BACS. Ця сфера потребує складних програм PLC для керування та забезпечення комфортного середовища, одночасно оптимізуючи ефективну роботу систем енергозабезпечення будівель (BES). Існує чіткий попит на добре визначений цифровий робочий процес для забезпечення автоматичного впровадження логіки керування у PLC для BACS.

У сфері BACS для цифровізації проєктування та реалізації логіки керування розробляються різні формати даних, окрім IFC, для обміну інформацією між інструментами програмного забезпечення та розробниками логіки керування.

ISO 16484-3 [29] вводить вимоги, що охоплюють програмне забезпечення та функції для BACS, та надає зразок шаблону для документування функціональних блоків, визначених під час проєктування, який називається списком функцій BACS. У списку функцій BACS входи та виходи функціональних блоків, параметри, що визначають функціональні блоки, відповідні дані датчиків та їх внутрішня логіка керування представлені у вигляді електронної таблиці. Однак список функцій BACS не може забезпечити формальний опис логіки керування та достатній опис складних і нестандартних функцій керування.

Проєкт OpenBuildingControl [14] розробив мову опису керування (CDL) для обміну визначеною логікою керування для систем опалення, вентиляції та кондиціонування повітря (HVAC). CDL базується на мові моделювання Modelica, яка не займається представленням знань, а компонентно-орієнтованим моделюванням та симуляцією складних систем [59]. Метод, розроблений у проєкті OpenBuildingControl, обмежується виключно використанням у системах HVAC і не дозволяє представляти ієрархічну логіку керування. Можливість трансляції мови опису керування (CDL) у мови програмування, що підтримуються IEC 61131-3, визнається, проте поки що не реалізована. Підходи до моделювання на основі онтологій для опису логіки керування у BACS також часто зустрічаються у багатьох роботах.

Дослідження, що намагаються застосувати IFC для опису логіки керування у BACS, є обмеженими. У роботі Chen та ін. [60] знання керування будівлею визначаються як знання про логіку керування, алгоритми, структуру керування та функціональні можливості технічного обладнання у будівлях. Для обміну знаннями з керування використовується схема бази даних M-BCK [61]. Автори цієї роботи [60] зазначають, що логіка керування та її представлення у мовах програмування зазвичай залежать від виробників і часто представлені у різних форматах та мовах програмування. Таким чином, ця робота лише надає схему даних для представлення загальних знань з керування будівлею без розгляду реалізації модулів керування, що описані у схемі даних. У роботі згадується потенціал інтеграції M-BCK у схему IFC, проте обговорення є обмеженим. Benndorf та ін. [62] докладають зусиль для розширення схеми IFC для опису деякої типової логіки керування у HVAC, такої як керування за кривими опалення, графіками часу та ПІД-контролерами. На основі цього методу схема IFC може містити інформацію про будівлі, їх технічні системи та відповідні функції керування. Однак цей метод документування не може повністю гнучко описувати визначені функції керування, а лише попередньо визначену логіку керування у схемі IFC. Ці роботи [11,63,64] вказують на відсутність формальної семантики IFC та підкреслюють переваги мови, заснованої на логіці, для представлення знань з керування. На основі цього у кількох роботах [5,10,11,65–67] обговорюється трансляція специфікації схеми EXPRESS, що представляє схему IFC, у мову онтологій.

Хоча існуючі методи покращують експлуатацію будівель, існує критичний пробіл щодо робочого процесу, який дозволяє автоматично реалізовувати функції керування, описані у цих форматах, що перешкоджає ефективному впровадженню функцій керування.

#### 2.1.1. Ієрархічна структура керування у схемі IFC

Як демонструє MODI [18], енергетичну систему можна розкласти на багаторівневу ієрархічну структуру на початку процесу проєктування керування. Як показано на рисунку 2a, ця ієрархічна структура складається з рівня мережі, рівня підсистеми, рівня компонента та рівня виконавчого механізму. На кожному рівні визначаються робочі режими, які описують специфічну поведінку системи. Послідовно встановлюється відповідна стратегія керування на основі режимів шляхом вибору використовуваних робочих режимів та визначення відповідних умов перемикання режимів. Для моделювання та виконання логіки керування на основі процесу перемикання режимів у SIPN ми застосовуємо підхід моделювання на основі SIPN [19] (рисунок 2b). Кожен робочий режим перетворюється на місце SIPN, тоді як умови перемикання режимів реалізуються як переходи у SIPN. При виконанні умови перемикання режиму відповідний перехід у SIPN активується, і маркер може бути переданий від вхідного місця до вихідного місця SIPN. Після отримання маркера вихідне місце активується для виконання відповідного робочого режиму, який реалізується як вихідна функція цього місця.

#### 2.1.2. Логіка керування, описана у SIPN, у схемі IFC

На основі ієрархічної структури ми починаємо перетворювати SIPN у об'єкти IfcController. SIPN може бути реалізована за допомогою новоствореного та об'єктивованого набору властивостей, який призначається для IfcController через зв'язок IfcRelDefinedByProperties. Як показано на рисунку 3, набір властивостей містить два типи властивостей, тобто IfcSimpleProperty та IfcComplexProperty. IfcSimpleProperty є об'єктом одиничної властивості, що містить різні підтипи, такі як IfcPropertySingleValue, IfcPropertyEnumeratedValue та IfcPropertyListValue. У нашому випадку ми використовуємо IfcPropertySingleValue для повідомлення деякої допоміжної інформації, наприклад, мінімального часу між двома перемиканнями режимів у SIPN. Порівняно з IfcPropertySingleValue, IfcComplexProperty дозволяє використовувати змішану колекцію підтипів IfcProperty, а також може бути включена як одиничний елемент властивості у IfcPropertySet. Ми використовуємо IfcComplexProperty для документування основної інформації SIPN.

#### 2.1.3. Зв’язок між контролерами та фізичними системами у схемі IFC

Для виконання процесу керування контролеру необхідно збирати інформацію від відповідних датчиків та керувати виконавчими механізмами для реалізації логіки керування. Усі відповідні датчики та виконавчі механізми також можуть бути задокументовані у схемі IFC, як показано на рисунку 5. Сутність IfcController пов’язується із сутностями IfcSensor та IfcActuator через зв’язок вкладення IFC IfcRelNests та порт розподілу IFC IfcDistributionPort. IfcRelNests використовується для вкладення впорядкованих колекцій елементів за допомогою двох атрибутів: RelatingObject та RelatedObjects. Застосовні цільові об’єкти можуть бути непроявленими підтипами, такими як контролери та процеси, або фізичними підтипами, а саме елементами, що мають порти. IfcDistributionPort представляє порти розподілу, які можуть бути призначені елементам IFC за допомогою IfcRelNests. Ці порти розподілу розглядаються як інтерфейси для позначення ролі елементів у певній системі, таких як вхід води або вихід даних. Атрибут FlowDirection визначає напрям потоку як Sink (вхід) або Source (вихід). У нашому випадку використовувані сутності IFC (IfcController, IfcSensor та IfcActuator) містять порти розподілу, визначені через IfcDistributionPort, для позначення потоку даних від сутностей IfcSensor до сутностей IfcController та команд від сутностей IfcController до сутностей IfcActuator.

### 2.2. Автоматизована реалізація алгоритмів керування на основі режимів, описаних у IFC, у ПЛК

Для автоматичної реалізації алгоритмів керування на основі режимів у ПЛК ми насамперед розробляємо методологію для перетворення алгоритмів керування на основі режимів, описаних у IFC, у сегменти коду ST, а потім реалізуємо цю методологію у середовищі .Net для досягнення програмно підтримуваного автоматизованого процесу реалізації алгоритмів керування на основі режимів у ПЛК.

#### 2.2.1. Реалізація алгоритмів керування на основі режимів, описаних у IFC, у ST

Основні питання реалізації алгоритмів керування на основі режимів, описаних у IFC, у ST наведені нижче:

- Відображення ієрархічно структурованих алгоритмів керування на основі режимів, виражених у схемі IFC, у відповідні ієрархічні програми ПЛК

- Одноразова відповідність властивостей IFC сегментам коду ST

Попередні роботи [20] показали ієрархічну структуру програмних організаційних одиниць (POU), що дозволяє реалізовувати алгоритми керування на основі режимів у ПЛК. На основі цього нам потрібно лише відобразити алгоритми керування на основі режимів, описані у IFC, у структуру програм (PRG) ПЛК. У цій роботі ми реалізуємо алгоритми керування на основі режимів, представлені у мережевих сутностях IfcController, у PRG, як показано на рисунку 6. Ієрархічна структура цих сутностей IfcController розпізнається через зв’язок IfcRelAggregates та відображається у FB у структурі POU. Входи та виходи кожної сутності IfcController, що описують обмін даними між різними рівнями, перетворюються на глобальні змінні та публічні властивості у PRG.

#### 2.2.2. Програмно підтримувана генерація ST для реалізації алгоритмів керування на основі режимів, описаних у IFC, у ПЛК

У цьому розділі ми розробляємо програмно підтримуваний підхід у середовищі .Net для імпорту даних IFC як джерела даних, перетворення даних IFC у дані JSON, а потім автоматичної генерації коду ST та його реалізації у програмах ПЛК. Для генерації та налаштування програм ПЛК використовується програмне забезпечення TwinCAT (Windows Control and Automation Technology) та інтерфейс TwinCAT Automation Interface, що розповсюджується компанією Beckhoff [56]. TwinCAT дозволяє використовувати об’єктно-орієнтовані мови програмування, визначені стандартом IEC 61131-3, для програмування проєктів ПЛК. TwinCAT Automation Interface забезпечує зв'язок між проєктами ПЛК у TwinCAT та зовнішніми середовищами на основі мов програмування, сумісних із COM, таких як .NET або C++, для створення та керування проєктами у зовнішньому середовищі. Таким чином, ми можемо створювати сценарії для безпосередньої генерації та налаштування проєктів ПЛК у TwinCAT замість ручного програмування.

### 3.1. Документування стратегії керування на основі режимів для обраної енергосистеми

На рисунку 14 показано схему системи та ієрархічну структуру системи енергозабезпечення, що складається з теплового насоса, теплового акумулятора, котла та споживача енергії. Тепловий акумулятор та котел забезпечують теплопостачання, тоді як тепловий насос подає гарячу воду до теплового акумулятора. Повітряно-водяний теплообмінник виступає як споживач енергії, у якому подана гаряча вода нагріває подане повітря у повітроводі. Виходячи з цієї схеми, ми розкладаємо систему на ієрархічну структуру відповідно до методу MODI. Ця енергосистема розглядається як мережа теплопостачання (HSN) на рівні мережі, яка може бути розділена на дві підсистеми теплопостачання (HSS) на рівні підсистеми, а саме HSS1 та HSS2. На рівні компонентів одна підсистема включає тепловий акумулятор та котел, інша — лише тепловий насос. Для кожного компонента визначаються відповідні виконавчі механізми.

![image-20250705105551679](media/image-20250705105551679.png)

Рисунок 14. Схема та ієрархічна структура системи енергозабезпечення. HSN: мережа теплопостачання; HSS: підсистема теплопостачання; HP: тепловий насос; HS: тепловий акумулятор; B: котел; HD: теплоспоживання; V: клапан; P: насос.

Рисунок 15. Документування ієрархічної структури керування та робочих режимів, застосованих до обраної енергосистеми на основі схеми IFC. HSN: мережа теплопостачання; HSS: підсистема теплопостачання; HP: тепловий насос; HS: тепловий акумулятор; B: котел; HD: теплоспоживання; V: клапан; P: насос.

Для завершення стратегії керування необхідно визначити умови перемикання режимів для цих робочих режимів. На рівні мережі HSN складається з HSS1 та HSS2. Під час роботи HSN підсистема HSS1 може задовольняти теплові потреби, тоді як HSS2 не може безпосередньо подавати тепло споживачу, але заряджає тепловий акумулятор HSS1. Таким чином, ми обираємо Режим 0 та Режим 3 для цього рівня та визначаємо перехід між цими двома робочими режимами залежно від потреби. Коли мережа увімкнена (є потреба), працюватимуть HSS1 та HSS2. Інакше обидві підсистеми вимикаються. На рівні підсистеми робота HSS2 визначається вихідними даними рівня мережі. Якщо HSS2 працює, температура у тепловому акумуляторі додатково визначає роботу теплового насоса у HSS2. При роботі HSS2, якщо тепловий акумулятор порожній, тепловий насос заряджатиме тепловий акумулятор. Інакше тепловий насос вимикається. У HSS1 тепловий акумулятор надає перевагу подачі тепла, якщо HSS1 працює і акумулятор не порожній. Котел підтримує подачу тепла лише тоді, коли акумулятор не може розрядитися для покриття теплоспоживання. На рівні компонентів робота компонентів визначається використовуваним робочим режимом на рівні підсистеми.

Ця стратегія може бути закодована у схемі IFC за допомогою методу документування на основі IFC. Для прикладу ми використовуємо стратегію керування на рівні мережі для опису цього процесу. Як показано на рисунку 16, визначені три екземпляри IfcPropertyEnumerationValue: “Operating modes”, “Transition conditions” та “Output” для HSN, які відповідно містять робочі режими, умови переходів та підсистеми HSN. Ми обираємо значення перерахувань цих екземплярів IfcPropertyEnumerationValue для опису процесу перемикання режимів та фіксуємо їх у екземплярах IfcPropertyListValue. Наприклад, рисунок 16 демонструє перехід від Режиму 0 до Режиму 3, коли останнім використовуваним режимом був Режим 0, і виконується умова переходу, позначена червоним. Режим 3 із (1,1) декодується екземпляром IfcPropertyEnumerationValue “Output” для вказівки, що HSS1 та HSS2 працюватимуть при активації цього режиму. Таким чином, бажані умови перемикання режимів на рівні мережі для цієї енергосистеми фіксуються у схемі IFC на основі IfcController HSN та його пов’язаних властивостей.

### 3.3. Оцінювання реалізованої стратегії керування за допомогою моделювання

У цьому розділі ми моделюємо енергосистему мовою моделювання Modelica [59] (далі — модель системи) та використовуємо Functional Mock-up Interface (FMI) [72] для інтеграції моделі системи у Python. Згенеровану програму ПЛК також можна інтегрувати у Python за допомогою пакету Pyads [73]. Після цього проводиться оцінювання програми ПЛК на основі моделювання для перевірки відповідності функціоналу програми ПЛК запланованим функціям керування.

Для моделювання системи використовуємо Modelica Standard Library, Aixlib [74] та Buildings [75]. Aixlib забезпечує модель акумулятора та модель теплового насоса, що включає виміряні дані для відображення продуктивності теплового насоса. Модель котла з бібліотеки Buildings використовується із можливістю параметризації типу палива, уставки температури та необхідної потужності котла. Виміряні дані комерційної будівлі у Люнебурзі імпортуються як умови [18,76]. Як показано на рисунку 21, ці виміряні дані включають температуру довкілля та теплоспоживання будівлі протягом двох тижнів січня. Температура випаровувача та температура конденсатора для теплового насоса відповідно задані як 14 °C та 45 °C. Бажана температура мережі теплопостачання становить 40 °C, тому акумулятор має повністю заряджатись при температурі акумулятора (THS) > 45 °C та повністю розряджатись при THS < 40 °C, щоб забезпечити досягнення необхідної температури мережі. Виходячи з цього, SOC встановлюється у FALSE при THS > 45 °C та у TRUE при THS < 40 °C. У діапазоні між 40 °C та 45 °C SOC не змінюється. Аналогічно SOC, SOD встановлюється у FALSE при THS < 40 °C та у TRUE при THS > 43 °C.

### 3.4. Обговорення

Результати прикладу використання демонструють методологію документування алгоритмів керування на основі режимів у схемі IFC та автоматичної реалізації цих алгоритмів у ПЛК для систем енергозабезпечення будівель (BES). На основі програмно підтримуваного підходу стратегія керування, задокументована у IFC, конфігурується у ПЛК шляхом автоматичної генерації коду ST та подальшого тестування на етапі моделювання.

Виходячи з MODI, алгоритми керування на основі режимів проєктуються у заздалегідь визначеній ієрархічній структурі та описуються у SIPN на етапі проєктування BACS. Для цих алгоритмів ми розробили структуру документування у схемі IFC, яка складається з ієрархічно структурованих сутностей IfcController, що дозволяє забезпечити одноразову відповідність від алгоритмів, описаних у SIPN, до алгоритмів, описаних у IFC. У цьому процесі ієрархія алгоритмів та відповідна логіка керування відображаються у вигляді ієрархічно вкладених сутностей IfcController та відповідних наборів властивостей. Ця структура представляє ієрархію керування та фіксує всі запроєктовані перемикання режимів у форматі списку у схемі IFC. Таким чином, немає потреби у додатковій інтерпретації між етапом проєктування та процесом документування. Проєктанти також можуть безпосередньо перевіряти перелічені шаблони місце-перехід-місце відповідно до ієрархії керування для забезпечення точного документування запланованої логіки керування. Крім того, ця структура документування повністю базується на існуючій схемі IFC, що дозволяє безпосередньо інтегрувати її у робочі процеси будівельних проєктів, у яких використовуються BIM та IFC.

У процесі реалізації одноразова відповідність додатково використовується для перетворення даних IFC у програму ПЛК. Для збереження ієрархічної структури керування програма ПЛК у прикладі використання складається з ієрархічно побудованих POU, що відображають ієрархічно вкладені сутності IfcController. У межах сутності IfcController кожен шаблон місце-перехід-місце, зафіксований у його наборі властивостей, реалізується у вигляді конструкції IF для виконання відповідного процесу перемикання режимів. Після перемикання режиму реалізується серія конструкцій IF для перевірки визначеного режиму та виклику його вихідної функції. Такий метод реалізації дозволяє уникнути створення складної логіки умов IF для перемикання режимів, оскільки створюються окремі конструкції IF для кожного шаблону місце-перехід-місце, що суттєво зменшує складність і кількість помилок під час автоматизованої генерації коду та допомагає програмістам розуміти та перевіряти згенерований код. Крім того, розроблене програмне забезпечення полегшує застосування автоматизованого підходу до реалізації. У прикладі використання достатньо запустити Python-скрипт для конвертації даних IFC, а потім імпортувати отриманий файл JSON через GUI. Усі POU, які потрібно згенерувати, відображаються з параметрами у GUI. Параметри, зафіксовані у IFC, можна перевірити у GUI, і є можливість доповнити відсутню інформацію у даних IFC, яка може вперше визначатися на етапі реалізації.

Результати моделювання підтверджують доцільність методології реалізації алгоритмів керування на основі режимів у ПЛК. ПЛК забезпечує процес перемикання режимів в ієрархічній структурі керування та відповідно визначає використовувані робочі режими згідно із запланованою стратегією керування. Фактична температура поданого повітря відповідає вимогам керування, утримуючись навколо уставки з похибкою в межах 1 °C.

Уся процедура застосування інструменту для генерації програми ПЛК у прикладі використання займає 15 хвилин, включаючи імпорт файлу IFC, запуск Python-скрипту для конвертації файлу IFC у файл JSON, перевірку та доповнення параметрів для всіх використовуваних FB та генерацію програми ПЛК. Інформацію про згенеровану програму наведено у таблиці 4. Для порівняння проводимо ручне програмування програми ПЛК для реалізації запроєктованої логіки керування з використанням стандартних об’єктів FB. Цей процес займає 2 години, якщо програміст має глибокі знання програмування ПЛК та методів реалізації алгоритмів керування на основі режимів. ## 4. Висновки

Програмування функцій керування у BACS завжди є трудомістким та затратним за часом завданням у будівельних проєктах. Цифровізація документування логіки керування у BACS досі недостатньо розвинена. У цій роботі представлено метод документування для фіксації алгоритмів керування на основі режимів у схемі IFC та програмно підтримуваний метод для автоматичної генерації коду ПЛК мовою Structured Text для реалізації алгоритмів керування на основі режимів у BACS. Ієрархічна структура керування алгоритмів керування на основі режимів була перетворена в ієрархічно структуровані сутності IfcController, тоді як логіки керування, описані у SIPN, були відображені у попередньо визначені сутності IfcPropertySet, пов’язані з відповідними сутностями IfcController. На основі цієї структури документування у даних IFC було застосовано одноразову відповідність для перетворення даних IFC у сегменти коду Structured Text в ієрархічно структурованій програмі ПЛК. Кожна сутність IfcController була реалізована у функціональному блоці шляхом трансляції її набору властивостей у код Structured Text. Цей метод генерації коду був запрограмований у інструменті, що забезпечує GUI для імпорту даних IFC та візуалізації та перевірки згенерованих FB. Ми використали цей інструмент для реалізації алгоритму керування на основі режимів для мережі теплопостачання у прикладі використання та протестували згенеровану програму ПЛК на етапі моделювання. Результати прикладу використання довели, що запланований алгоритм керування на основі режимів був дійсно зафіксований у даних IFC та зчитаний інструментом для генерації відповідної програми ПЛК. У даних IFC ієрархічні сутності IfcController та їхні властивості відображали бажану структуру керування та логіку керування, описану у сигнально-інтерпретованих мережах Петрі. Ці дані IFC були успішно реалізовані у програмі ПЛК для виконання бажаної логіки керування та визначення використовуваних робочих режимів.

Метод документування на основі IFC дозволяє інтегрувати проєктування логіки керування для BACS безпосередньо у поточні робочі процеси будівельних проєктів, використовуючи IFC як цифрове джерело даних. Цей метод розроблено на основі існуючої схеми IFC, і не потрібно додаткових зусиль для розширення схеми IFC для документування алгоритмів керування. Крім того, використання цього інструменту дозволило значно скоротити витрати часу та кількість помилок під час програмування. Замість ручного програмування повних програм ПЛК або копіювання-вставки з подальшою переконфігурацією існуючих програм, програмістам потрібно лише імпортувати дані IFC, після чого перевірити та доповнити кожен FB для реалізації алгоритмів керування. У цьому процесі програмісти можуть зосередитися лише на параметризації FB на кожному рівні, не потребуючи побудови всіх алгоритмів керування у ПЛК та загального огляду складних зв’язків керування. Реалізовані алгоритми керування також можуть містити гнучкішу логіку керування, ніж копіювання з існуючих програм ПЛК. Проте важливо зазначити, що деякі функції керування, такі як ПІД-регулятори, у згенерованих програмах ПЛК потребують налаштування для узгодження зі специфічними вимогами системи. Крім того, користувачам необхідно перевіряти та доповнювати параметри функціональних блоків, якщо у форматі IFC відсутні деякі параметри.

У майбутніх дослідженнях планується проведення апаратного тестування за методом hardware-in-the-loop для подальшої оцінки цієї методології у практичній фазі. Стандартні алгоритми керування на основі режимів для агрегатів обробки повітря також будуть інтегровані у цю методологію як конкретний приклад використання для розширення її застосування.
